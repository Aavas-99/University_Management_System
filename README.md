# University Management System

A learning project for a small university management web application built with
Java 21, Spring Boot, Spring Security, Thymeleaf, and PostgreSQL. It provides
role-protected record pages and JSON REST APIs for Admin, Teacher, and Student
accounts.

## 1. What happens when the app runs?

1. Spring Boot starts the web server and reads settings from
   `src/main/resources/application.properties`.
2. Spring Data JPA connects to PostgreSQL and maps the `UniversityUser` entity
   to a database table.
3. If there are no admin accounts yet, the app creates one from the `APP_ADMIN_*`
   settings. Its password is encoded with BCrypt before it is saved.
4. Spring Security checks login credentials and the user's role before allowing
   access to a page or API endpoint.
5. MVC controllers render record pages with Thymeleaf; REST controllers provide
   JSON endpoints. Both use the service for account rules and the repository
   for database access.

## 2. Run locally from IntelliJ IDEA (no Docker)

You need **JDK 21**, **IntelliJ IDEA**, and a local **PostgreSQL 17** server.
Docker is not required for this workflow. The app expects the database to be
available at `localhost:5432`.

### Prepare PostgreSQL once

Start PostgreSQL from Windows Services or pgAdmin. In pgAdmin's Query Tool (or
`psql`), create a local database account and database. Replace the sample
password with one of your choice:

```sql
CREATE USER university_user WITH PASSWORD 'your-local-password';
CREATE DATABASE university_db OWNER university_user;
```

### Open and run the project

1. In IntelliJ, choose **File > Open** and select this project's `pom.xml` (or
   the project folder). Choose **Open as Project** and allow Maven to import.
2. Set **Project SDK** and the Maven runner JDK to **Java 21** in
   **File > Project Structure** and **Settings > Build, Execution, Deployment
   > Build Tools > Maven**.
3. If IntelliJ did not automatically import Maven, open the Maven tool window
   and click **Reload All Maven Projects**.
4. Open **Run > Edit Configurations**. A shared
   `UniversityManagementApplication` run configuration is provided under
   `.run/`. If IntelliJ does not load it, create an **Application**
   configuration with main class
   `com.university.university_management.UniversityManagementApplication` and
   the `university-management` module.
5. In that run configuration's **Environment variables**, set your own initial
   admin credentials and the local database connection:

   ```text
   SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/university_db
   SPRING_DATASOURCE_USERNAME=university_user
   SPRING_DATASOURCE_PASSWORD=your-local-password
   APP_ADMIN_EMAIL=your-admin-email@example.edu
   APP_ADMIN_PASSWORD=your-strong-password
   ```

6. Click **Run** (green triangle). IntelliJ compiles the project, creates the
   database table, and inserts this admin if the configured email is not
   already in use. The password is BCrypt-hashed before it is stored in
   `university_users`; do not insert a plain-text password directly in SQL.
7. Open <http://localhost:8080> and sign in with the configured admin email and
   password.

The credentials above are local examples. Change them for your machine and do
not commit passwords. A developer can also start the app with
`.\mvnw.cmd spring-boot:run` from PowerShell after setting the same environment
variables.

### Run automated tests

Tests use an in-memory H2 database and do not need PostgreSQL to be running:

```powershell
.\mvnw.cmd test
```

### Docker (optional, later)

The existing `Dockerfile` and `compose.yaml` remain available if you want to
learn containerization later. You can ignore them while developing and running
the application from IntelliJ. To use Compose, copy `.env.example` to `.env`, edit
`APP_ADMIN_EMAIL` and `APP_ADMIN_PASSWORD` in `.env` to credentials you choose,
then run `docker compose up --build`. Compose passes those credentials to the
application, which adds the configured admin to PostgreSQL if that email is
not already registered.
The `.env` file is ignored by Git and should never be committed.

## 3. Learn the code structure

All Java packages are under `src/main/java/com/university/university_management/`.

| Area | Purpose |
|---|---|
| `model/UniversityUser.java` | JPA entity: the account fields stored in PostgreSQL. |
| `model/UserRole.java` | The three allowed roles and their REST resource names. |
| `repository/UniversityUserRepository.java` | Database operations generated by Spring Data JPA. |
| `dto/UserRequest.java` | Validates JSON data sent by a caller. |
| `dto/UserResponse.java` | Safe JSON response shape; intentionally leaves out password hashes. |
| `service/UniversityUserService.java` | CRUD rules, role filtering, duplicate-email handling, and password encoding. |
| `controller/UserController.java` | Maps REST URLs and HTTP verbs to the service. |
| `controller/AuthController.java` | Returns the signed-in user and a CSRF token for API clients. |
| `controller/PageController.java` | Selects the simple home and login pages. |
| `config/SecurityConfig.java` | Login, logout, CSRF, password encoder, and URL-based role rules. |
| `config/DefaultAdminInitializer.java` | Creates the first admin account when the database has none. |
| `src/main/resources/templates/` | Thymeleaf HTML pages. |
| `src/main/resources/application.properties` | Database and app defaults; environment variables override them. |
| `compose.yaml` / `Dockerfile` | Runs PostgreSQL and the packaged Java application in containers. |

### Browser record workflow

After signing in, use the home page's **Records** links to view accessible
accounts as an HTML table at `/records/admins`, `/records/teachers`, or
`/records/students`. Tables include Edit and Delete actions, with access
following the same role boundaries as the API. Student signup requires name,
roll, department, batch, email, and password. Teacher signup requires name,
department, designation, email, and password. An authenticated Admin can create
another Admin account with email and password; Admin registration is not open
to anonymous visitors. API endpoints under `/api/` remain available to clients
that need JSON.

The configured admin is seeded at application startup from `APP_ADMIN_EMAIL`
and `APP_ADMIN_PASSWORD` when that email is not already registered. The account
is saved in the `university_users` table with a BCrypt password hash. To add
more admins, sign in as an Admin and use **Create an Admin account** on the home
page.

### Important Spring / Java ideas

- **Entity:** `UniversityUser` is a Java object that JPA stores as a database
  row. The enum role is persisted as readable text (`ADMIN`, `TEACHER`, or
  `STUDENT`).
- **Repository:** `UniversityUserRepository` extends `JpaRepository`, so Spring
  supplies common database operations. Method names such as
  `findAllByRoleOrderByIdAsc` describe the query Spring should generate.
- **DTO:** a Data Transfer Object is the public shape of an HTTP request or
  response. Separating it from the entity prevents clients from choosing their
  own role and prevents password hashes from appearing in JSON.
- **Controller:** maps an HTTP method and URL to Java code. For example,
  `POST /api/students` creates a student and returns HTTP `201 Created`.
- **Service:** keeps application rules out of the web layer. It hashes
  passwords, checks email uniqueness, and filters results by the resource's
  role.
- **Dependency injection:** Spring creates components such as controllers,
  services, and repositories, then supplies their dependencies through
  constructors.
- **Bean validation:** annotations like `@NotBlank`, `@Email`, and `@Size` reject
  malformed requests with HTTP `400 Bad Request`.
- **BCrypt:** passwords are one-way encoded, not stored as clear text. A login
  checks the submitted password against the stored hash.
- **Session authentication:** login creates an authenticated server session.
  The browser keeps a session cookie and sends it on subsequent requests.
- **CSRF:** because browser sessions use cookies, state-changing requests must
  include a CSRF token. The Thymeleaf forms include it automatically. API
  clients can fetch one from `GET /api/auth/csrf` and send the returned value in
  the header named by its `headerName` field (currently `X-CSRF-TOKEN`) along
  with the cookie.
- **Docker Compose:** starts the database and app as separate services. The app
  connects to the database using the Compose service name `postgres`, not
  `localhost`.

The application currently uses Hibernate `ddl-auto=update` to make this learning
project easy to start. For a real deployment, use database migrations (such as
Flyway), enforce HTTPS, use strong secrets, and review the deployment security
settings before going live.

## 4. REST API

All resource endpoints use JSON. Password is required on creation and must
contain at least eight characters. A `PUT` updates account details; omit or
leave its password blank to keep the current password. Student requests require
name, roll (or legacy `studentNumber`), department, batch, email, and password
on create. Teacher requests require name, department, designation, email, and
password on create. Admin requests require email and password. The API assigns
the role from the URL; callers cannot promote their own account by adding a
`role` field.

| Resource | Collection URL | Who can use it |
|---|---|---|
| Admins | `/api/admins` | Admin |
| Teachers | `/api/teachers` | Admin and Teacher |
| Students | `/api/students` | Admin and Student for all methods; Teacher for read, update, and delete |

For each collection, the supported operations are:

| Method | URL | Result |
|---|---|---|
| `POST` | `/api/{admins,teachers,students}` | Create; `201 Created` and a `Location` header |
| `GET` | `/api/{admins,teachers,students}` | List; `200 OK` |
| `GET` | `/api/{admins,teachers,students}/{id}` | Read one; `200 OK` |
| `PUT` | `/api/{admins,teachers,students}/{id}` | Replace; `200 OK` |
| `DELETE` | `/api/{admins,teachers,students}/{id}` | Delete; `204 No Content` |

Other useful status codes are `400` for invalid input, `401` if not signed in,
`403` if the signed-in role is not allowed, `404` if the resource/account does
not exist, and `409` for duplicate email (or deleting the last admin).

Additional role-scoped resources:

| Method | URL | Purpose |
|---|---|---|
| `GET` | `/api/dashboard` | Returns the signed-in role and counts for its permitted account resources. |
| `GET` | `/api/profile` | Returns the signed-in account without its password hash. |
| `PATCH` | `/api/accounts/{id}/status` | Admin-only; update an account's `active` state with `{"active": false}` or `{"active": true}`. Disabled accounts cannot sign in. The last active admin cannot be disabled. |

Example create body:

```json
{
  "name": "Ayesha Rahman",
  "email": "ayesha@example.edu",
  "password": "StudentPass123!",
  "department": "Computer Science",
  "roll": "CSE-2026-001",
  "batch": "2026"
}
```

Use the browser's records pages for HTML tables and account changes. To use the
API, send the JSON body as a `POST` to the corresponding URL using an API client
such as Postman; include the session cookie and CSRF token.
For example, the browser's sign-in uses a form post to `/api/auth/login`, and
logout is a CSRF-protected `POST /api/auth/logout`.

Useful authentication endpoints:

| Method | URL | Purpose |
|---|---|---|
| `POST` | `/api/auth/login` | Form-encoded `username` (email) and `password`; creates a session. |
| `POST` | `/api/auth/logout` | Ends the current session. |
| `GET` | `/api/auth/me` | Returns the current user's email and roles. |
| `GET` | `/api/auth/csrf` | Returns a CSRF token for API clients. |

## 5. Git and GitHub workflow

This folder is prepared for GitHub: `.env` is ignored, and `.env.example` shows
the settings contributors need. To publish it:

1. Create an **empty** repository on GitHub (do not add a README there, since
   this project already has one).
2. In PowerShell, from the project directory, initialize and push:

   ```powershell
   git init
   git add .
   git status
   git commit -m "Build university management learning app"
   git branch -M main
   git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
   git push -u origin main
   ```

3. For each feature, create a branch, make small commits, push it, and open a
   pull request:

   ```powershell
   git switch -c feature/add-course-resource
   git add .
   git commit -m "Add course resource"
   git push -u origin feature/add-course-resource
   ```

Review `git status` before committing and never add `.env`, passwords, or other
secrets. After copying `.env.example` to `.env`, Git continues to ignore the
actual local settings.
